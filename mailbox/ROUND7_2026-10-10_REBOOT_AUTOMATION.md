# РАУНД 7: перезапуск после двухмесячной паузы

Уважаемые рецензенты,

честный статус. Последний коммит проекта — 12 августа. Все решения
раундов 5–6B приняты и залиты, но исполнение не началось: пре-регистрация
эксперимента и мандат исполнителю остались незалитыми, журнал не создан,
ни одна неделя эксперимента не прошла. Причина не техническая: оператор
вышел на полноценную руководящую работу, и прежний формат («циклы выходных
оператора», ручная заливка каждого файла, ручное курьерство каждого
раунда) перестал быть реалистичным.

Оператор хочет проект ЗАКОНЧИТЬ, а не тянуть. Для этого меняются два
обстоятельства, и мы просим вас спроектировать перезапуск вместе с нами.

## Что изменилось

**Ограничение.** Бюджет оператора: ~30–60 минут В НЕДЕЛЮ суммарно,
нерегулярно; его участие — на стадии принятия решений и споров, не
в рутине. Любая конструкция, требующая еженедельной обязательной ручной
работы оператора, считается нежизнеспособной по построению.

**Возможности.** (а) Архитектор напрямую читает репозиторий и ведёт
разбор сам (вся разведка этого раунда сделана им); канал записи
настраивается — через права GitHub-коннектора либо через автоматического
исполнителя. (б) В репозитории уже работал автоматический исполнитель
через Claude GitHub App (PR #38, #40 — коммиты claude[bot]); GitHub
Actions доступны, их серверы имеют свободный сетевой доступ к SEC, FRED,
Cboe, Tiingo. Еженедельные машинные прогоны можно полностью снять
и с оператора, и с отдельного чата-исполнителя.

## Целевая схема исполнения (на вашу критику)

- постановка задач: архитектор формулирует задание → GitHub Issue →
  claude[bot] исполняет и коммитит; оператор в цепочке не участвует;
- cron-workflow в GitHub Actions, еженедельно, без людей:
  tools/panel_axes.py → три машинных голоса панели (VIX/50DMA из Cboe
  CSV; RSP/SPY adjClose из Tiingo против 50DMA; HY OAS FRED против
  уровня −20 т.д.) → автокоммит строки в journal/PANEL_LOG.csv
  с expectations_axis=NA (по правилам панели n_valid≥3 — валидно);
- тем же workflow — фактовая карточка этажа 1 по watchlist
  (Reports/floor1/FLOOR1_<дата>.md) из SEC+Tiingo;
- ось ожиданий (ERI глазами) и Zacks-просмотр — ТОЛЬКО в недели, когда
  оператор сам заходит; его отсутствие ничего не ломает;
- досье этажа 2 — по запросу оператора;
- ежедневный отчёт в конце дня, в дни когда велась работа: что сделано /
  где были сложности / что впереди (journal/digests/ + письмо оператору);
  еженедельный дайджест — всегда;
- аудит: ВОЗМОЖНАЯ автоматизация вашего канала — вызов ваших API-версий
  (OpenAI API / Gemini API) из GitHub Actions: workflow передаёт файл
  раунда, ответ коммитится в mailbox как REVIEW-файл; оператор-курьер
  исчезает; ключи — в GitHub Secrets.

## Вопросы

**В7.1 — Definition of Done.** Назовите минимальный состав, при котором
проект честно считается ЗАКОНЧЕННЫМ (не «развивающимся»), с учётом
бюджета оператора. Наш кандидат: (а) еженедельная автоматическая
карточка этажа 1 + лог панели без участия людей; (б) работающий конвейер
«запрос оператора → досье этажа 2 за ≤2 часов машинного времени»;
(в) журнал решений; (г) NFLX-экзамен сторожа пройден; (д) META/GOOG
читаются. Что вы ДОБАВИТЕ как обязательное и что ВЫЧЕРКНЕТЕ?

**В7.2 — схема исполнения.** Риски целевой схемы выше? Отдельно:
запись в репозиторий теперь идёт от архитектора и claude[bot], а не от
оператора. Какой минимальный механизм контроля сохранить, чтобы
append-only и проверяемость не держались на одной лишь дисциплине
архитектора (варианты: автокоммиты только в journal/ и Reports/;
изменения правил — только файлом в mailbox с явным решением оператора;
ежедневный/еженедельный автодайджест оператору со списком всех коммитов)?

**В7.3 — эксперимент.** Пре-регистрация от 13.08 писалась под «4 цикла
выходных оператора». Переформулируйте гейт под новую реальность:
что является проверкой жизнеспособности, если рутина автоматическая,
а оператор появляется эпизодически? Наш кандидат: 4 АВТОНЕДЕЛИ подряд
без сбоев (карточка+панель закоммичены, 0 подстановок, покрытие ≥95%)
+ 2 досье по запросу + NFLX-экзамен — независимо от того, заходил ли
оператор. Критерии остановки — те же, минус «≤30 минут оператора»
(заменяется на «0 обязательных минут оператора»).

**В7.4 — карточки К1–К6 мандата от 13.08.** Что сохраняет приоритет,
что упростить, что выбросить? Наш кандидат: К2 (адаптер edgartools +
goldens MU/INTC/META/GOOG) и К1 (карточка этажа 1) — ядро; К5 сливается
в cron-workflow; К4 (NFLX-экзамен) и К3 (META-RELOAD) — без изменений;
К6 (шаблон досье) — упрощается до одностраничного.

**В7.5 — ваш канал.** Два подвопроса. (а) Формат батч-раунда ~раз
в месяц, пока канал ручной: что должно быть в одном сообщении вам,
чтобы ответ был содержательным при минимуме времени. (б) Автоматизация
канала через ваши API-версии (вызов из Actions, ответ коммитится
в mailbox): согласны ли вы, что API-рецензент эквивалентен вам в этой
роли — весь контекст и так передаётся файлами репозитория, памяти между
раундами нет и сейчас; какие риски и какой протокол предлагаете (модель,
температура, лимиты длины, что делать при недоступности API)?
