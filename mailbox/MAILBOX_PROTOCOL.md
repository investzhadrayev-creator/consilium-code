# MAILBOX — протокол обмена длинными сообщениями через GitHub

**Проблема, которую он решает.** Длинные мандаты и доклады, вставляемые в чат целиком,
расходуют контекст всех участников: оператор носит текст буфером обмена, чат-получатель
получает простыню разом, история теряется при ротации. Симптомы — деградация чатов,
забытые мандаты, «ошибки по допущению вместо чтения источника».

**Принцип.** В чатах живут только короткие живые реплики. Всё длинное — файлом
в репозитории `consilium-code`, папка `mailbox/`. Получатель читает сам, ровно то,
что ему нужно, и может перечитать в любой момент.

---

## Правила для ВСЕХ чатов проекта (КОНСИЛИУМ, БАЗА, АРХИТЕКТОР)

### 1. Что идёт через mailbox

- мандаты архитектора длиннее ~10 строк;
- доклады чатов архитектору (приёмка чейнджсета, разбор пакета, диагностика);
- любые спецификации, ведомости дефектов, разборы отчётов;
- решения оператора, требующие точной формулировки.

Короткие реплики («принято», «залито», «жду», «стоп») остаются в чате.

### 2. Именование файлов

```
mailbox/MANDATE_<YYYY-MM-DD>_<NN>_<получатель>.md      от архитектора
mailbox/REPORT_<YYYY-MM-DD>_<NN>_<автор>.md            от чата-исполнителя
```

`<получатель>` / `<автор>`: `CONSILIUM`, `BASE`, `ARCHITECT`.
`<NN>` — порядковый номер за день, 01, 02, …
Пример: `mailbox/MANDATE_2026-08-05_01_CONSILIUM.md`.

**Имя файла не выдумывается.** Автор пишет то имя, которое реально создал; оператор
кладёт файл ровно под тем именем, которое ему назвали. Если имя не совпало —
сообщает автору, а не переименовывает молча.

**Имя НИКОГДА не переиспользуется.** Перед тем как назвать новый файл, автор
смотрит, что уже лежит в `mailbox/`, и берёт следующий свободный `<NN>`. Причина
механическая: заливка файла с существующим именем ПЕРЕЗАПИСЫВАЕТ прежний, и
получатель, читая имя из строки в чате, не может отличить новый документ от
затёртого старого. Один документ — одно имя навсегда.

Проверка перед именованием:

```bash
curl -sL https://codeload.github.com/investzhadrayev-creator/consilium-code/zip/refs/heads/main -o repo.zip
unzip -q -o repo.zip && ls consilium-code-main/mailbox/
```

Исправление документа — **не перезапись, а новая версия**: `..._02_...` с полем
`supersedes:` в шапке, указывающим на предыдущий файл. Прежний остаётся на месте:
история решений не переписывается — это то же правило append-only, что и в базе
знаний.

### 3. Как получатель читает

```bash
curl -sL https://codeload.github.com/investzhadrayev-creator/consilium-code/zip/refs/heads/main -o repo.zip
unzip -q repo.zip
cat consilium-code-main/mailbox/<имя файла>
```

Читать **только адресованный файл**. Не листать mailbox целиком: папка растёт,
и чтение чужой почты — прямой расход контекста без пользы.

### 4. Как отправитель пишет

- Файл самодостаточен: получатель не должен угадывать контекст из переписки.
- Шапка обязательна: `author`, `date`, `status`, при необходимости `supersedes`.
- Все числа, версии, имена файлов — из выхода инструментов, не по памяти.
- После заливки в чат идёт **одна строка**: «Исполни `mailbox/<имя>`» или
  «Доклад залит: `mailbox/<имя>`».

### 5. Сообщение в чат — СВОДКА ДЛЯ ОПЕРАТОРА, а не копия документа

Полный текст доклада или мандата в чат **не вставляется никогда**: он уже лежит
файлом, и повторение съедает контекст всех участников — ровно то, из-за чего проект
трижды терял чаты.

В чат идёт короткая сводка по фиксированной форме, максимум 6–8 строк, обычным
языком, без внутренних имён полей и нод:

```
Доклад залит: mailbox/<имя файла>

ЧТО ИЗМЕНИЛОСЬ: 1–3 строки — что сделано или найдено, по-человечески.
ЧТО ДАЛЬШЕ: 1–2 строки — следующий шаг и кто его делает.
ОТ ОПЕРАТОРА: что именно требуется — залить файл / задеплоить / запустить прогон /
              ничего не требуется.
```

Правила сводки:

- она для **оператора**, не для архитектора: архитектор прочитает файл сам;
- никаких простыней с обоснованиями, номерами пинов и мутаций — это всё в файле;
- если от оператора ничего не требуется, так и писать: «ничего не требуется»;
- деньги и время называются прямо: сколько стоит прогон, сколько займёт шаг.

Правило действует для **всех** участников, включая архитектора: его мандаты тоже
уходят файлом, а в чат идёт сводка той же формы.

### 6. Цикл обмена

```
Архитектор пишет файл → оператор заливает → одна строка в чат-исполнитель
   → исполнитель читает из репозитория, работает
   → пишет файл-доклад → оператор заливает → одна строка архитектору
   → архитектор читает из репозитория, принимает
```

Оператор в этой схеме — не курьер текста, а тот, кто нажимает «залить»
и передаёт одну строку.

### 7. Что НЕ меняется

- Код по-прежнему заливается распакованными деревьями `CONSILIUM_REPO_v4_2_NN/`.
- Отчёты прогонов — в `Reports/`, с теми именами, которые печатает конвейер.
- Приёмка — по сырому дереву из репозитория, не по докладу.
- Правила ротации чатов (граница по артефакту + аварийный сигнал) — без изменений.

## Отдельно для чата БАЗА

Всё вышеперечисленное действует и для линии Postgres. Дополнительно:

- ТЗ, DDL и мандаты вех живут в репозитории базы знаний `consilium-spine`
  (`01_specs/`), а не пересылаются в чат;
- отчёты о вехах и разборы — через `mailbox/` в `consilium-code` по тем же правилам;
- секретов (DATABASE_URL, ключи, chat_id) в mailbox нет никогда — правило публичного
  репозитория действует без исключений.

---

## Почему это важно

Проект уже трижды терял чаты от переполнения и получал дефекты передачи. Каждый
раз причина была одна: **истина жила в переписке, а переписка смертна.** Mailbox
доводит до конца принцип, из-за которого заведена база знаний: у каждого факта
и каждого поручения — один дом, доступный всем и переживающий любой чат.
