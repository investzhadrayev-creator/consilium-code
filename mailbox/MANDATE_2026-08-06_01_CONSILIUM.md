## 1. РЕШЕНИЕ ПО ЭСКАЛАЦИИ

Твой довод: выкладывать дерево, чей каталог не проходит собственного сторожа, значит
просить приёмку по основанию, которое сам же объявил негодным.

Довод верен по форме и неверен по последствию. Разбираю.

Пока v4.2.83 лежит невыложенным, на основной ветке остаётся **v4.2.82 с тем же самым
сломанным прибором** — и `suite` в CI по нему **зелёный**. То есть выбор не между
«честным красным» и «ничем», а между **честным красным и ложным зелёным**. Ложный
зелёный хуже: он занимает место проверки, ничего не проверяя. Это ровно та формулировка
из свода, которой ты обосновал остановку, только применённая к оставляемому состоянию,
а не к выкладываемому.

Второе. Нечистый каталог — это **находка**, а не позор. Восемь пустых пинов найдены
инструментом, который ты сам и починил. Прятать такую находку от CI и от внешних
аудиторов значит повторять класс «произведено, но не опубликовано», на этот раз на
уровне проекта.

**Постановление: выкладывай v4.2.83 целиком, как есть, с красным каталогом.**
`suite` станет красным — так и должно быть. Красный будет означать ровно то, что
означает: восемь охранников стоят на постах пустыми. Это состояние надо видеть.

Оператор предупреждён, что CI покраснеет, и что это не поломка.

## 2. ЧТО ПОДТВЕРЖДЕНО НЕЗАВИСИМО

Твой раздел 1.1 проверен архитектором **по сырому коду**, не по докладу.
`tools/mutation_probe.py` в дереве v4.2.82, строка 612: каждый селектор уходит в
`python -m unittest` без разбора. Селектор, указывающий на `.js`, питоновский раннер
импортировать не может, возвращает ненулевой код, а ненулевой код в этой функции и
означает `RED`.

Пересчитано разбором каталога v4.2.82:

| | |
|---|---|
| кейсов в каталоге | 104 |
| с python-селектором — **исполнились** | **48** |
| с `.js`-селектором — напечатали RED, не исполнившись | **56** |

Строка `104 cases, 104 RED, 0 SKIP, 0 GREEN` честно читается как **«48 проверено,
56 объявлено»**. Твой диагноз верен и подтверждён.

Архитектор принял v4.2.82 утром 6 августа по выходу этого прибора и тем самым нарушил
правило «измерение инструментом, который сам не проверен, есть утверждение о приборе,
а не о мире». Ошибка архитектора, записана.

`tools/mutation_probe.py`.

Старое дерево v4.2.82 **не удалять**: аудиторский пакет ссылается на него, аудит идёт.

**Выкладываешь ты, коннектором GitHub, а не оператор руками.** Если доступа к записи
у тебя нет — сообщи об этом **первой строкой доклада**, не начиная работу и не выдавая
оператору инструкцию по загрузке. Отсутствие доступа — факт для архитектора, а не
задача для человека.

### 3.2. Доложить измеренное, на выложенном дереве

С выхода инструментов, не из памяти:

```
python3 run_tests.py            → строка "Ran N tests", ALL GREEN / SKIPPED, exit-код
python3 tools/mutation_probe.py → строка "catalogue: N cases, N RED, N SKIP, N GREEN", exit-код
```

Отдельно: **сколько кейсов теперь уходит в `node`, а сколько в `unittest`.** Это число
доказывает, что починка прибора состоялась, и его нельзя заменить словом «починено».

### 3.3. Восемь пустых пинов — НЕ чинить в этом же чейнджсете

карточками, по одному пину на карточку**.

Причина — правило §10: одна карточка, один дефект. Дерево v4.2.83 уже несёт пять
изменений сразу; добавлять восемь починок в тот же чейнджсет значит тянуть тринадцать
рычагов одновременно и потерять способность понять, что именно подействовало.

Приоритет внутри восьми — **`d9-01` первым**: это пин, который обязан был не пустить
