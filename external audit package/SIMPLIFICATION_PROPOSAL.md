# SIMPLIFICATION_PROPOSAL.md — что можно убрать без потери результата

**Пакет:** external_audit_package · **дата:** 2026-08-05

Документ написан архитектором той системы, которую он предлагает урезать. Конфликт
интересов очевиден, поэтому по каждому пункту указано, **чем его проверить**, а не
только мнение.

**Что сохраняется во всех вариантах** (требование оператора): первичные данные SEC,
детерминированный расчёт, провенанс, отказ при недостатке данных вместо догадки,
машинный и человеческий отчёты, квартальные и ценовые алерты.

---

## 1. Бизнес-логика в n8n → Python-пакет

**Сейчас:** около 54 узлов в n8n, часть логики живёт в узлах кода внутри JSON-файла
воркфлоу. Отдельные строки достигают 58 000 символов.

**Издержки, наблюдаемые:** правки узлов делаются вставкой в JSON и трижды ломались из-за
экранирования; чтение воркфлоу переполняет контекст участников; проверки на узлы
приходится писать через разбор JSON; невозможно нормально сравнить версии.

**Предложение:** вся расчётная и рендерящая логика уходит в Python-пакет под контролем
версий; n8n остаётся оркестратором (расписание, вызовы, доставка), без бизнес-логики.

**Возражение:** миграция трогает денежный путь и требует полного перепрогона валидации.

**Чем проверить:** посчитать долю строк логики внутри JSON против модулей; посчитать
дефекты, вызванные редактированием JSON (в истории проекта их не меньше трёх).

**Оценка:** высокая польза, высокая цена. Делать после валидационной матрицы, не раньше.

## 2. Отказ от Flask

**Сейчас:** микросервис на Flask на Railway, вызывается только из n8n.

**Вопрос:** нужен ли HTTP-сервис, если внешних клиентов нет?

**Альтернатива:** вызывать тот же код библиотекой или скриптом; убирается развёртывание,
сетевой слой, различие версий между n8n и сервисом (класс «раздельный деплой», который
уже давал дефекты).

**Возражение:** n8n удобно вызывает HTTP; переход на другой способ вызова — работа.

**Чем проверить:** есть ли хоть один потребитель сервиса, кроме n8n. Насколько известно,
нет.

**Оценка:** польза средняя, цена низкая. Кандидат к исполнению вместе с пунктом 1.

## 3. Отказ от общего новостного поиска

**Сейчас:** поисковый ИИ опрашивается по темам; возвращает преимущественно обзорные
статьи.

**Измерения:** на прогоне ORCL живым оказался один раздел из четырнадцати; после
переработки контракта — шесть из одиннадцати на диагностическом прогоне; события
приходили годовой давности.

**Предложение:** отказаться от общего поиска и оставить **только события с датами**
из первоисточников: подачи в SEC (форма 8-K, изменения в 10-K), плюс, при необходимости,
один платный источник новостей.

**Что теряется:** контекст конкуренции и настроений — то, что и так почти не приходит.

**Чем проверить:** доля разделов, содержащих проверяемый факт с датой и источником,
за последние пять прогонов.

**Оценка:** польза высокая, цена низкая. Рекомендуется.

## 4. Отказ от балла качества 0–100

**Сейчас:** сводный балл из блоков (рост, прибыльность, баланс, ров, динамика).

**Против него:** балл гуляет между прогонами на одних данных (измерено: 64 и 62 у MA);
он не влияет на вердикт; он печатается рядом с детерминированными величинами и создаёт
ложное впечатление одинаковой надёжности; именно на нём произошёл самый дорогой дефект
скоринга (нулевой долг → 4 из 4).

**За него:** читателю нужна краткая характеристика бизнеса, а не только цена.

**Компромисс:** отказаться от **числа**, оставить блоки как перечень сильных и слабых
сторон с обоснованиями, без арифметики и без сводной оценки.

**Чем проверить:** сколько решений оператора за историю проекта опиралось на балл.
По имеющимся данным — ни одного.

**Оценка:** польза высокая. Рекомендуется в компромиссном виде.

## 5. Один основной LLM плюс один целевой red-team шаг

**Сейчас:** несколько провайдеров на разных стадиях, консилиум мнений плюс арбитр.

**Наблюдения:** одна из стадий была отключена год назад и всё это время печаталась
в отчёте о расходах как участник — обнаружено только сейчас; разброс качественных
суждений между моделями велик; арифметику ни одна из них не считает.

**Предложение:** один основной провайдер для анализа и один отдельный шаг «найди, где
это рассуждение неверно» с явно противоположной задачей.

**Что теряется:** разнообразие мнений — ценность которого **не измерялась**.

**Чем проверить:** сравнить вердикты на архивных прогонах при отключении отдельных
стадий. Данные для этого есть.

**Оценка:** польза средняя-высокая, цена низкая. Требует измерения перед решением.

## 6. Полный анализ только по существенным событиям

**Сейчас:** полный прогон запускается вручную по имени.

**Предложение:** полный дорогой прогон — при событии (новая годовая или квартальная
отчётность, движение цены за порог); в остальное время — дешёвая переоценка по цене
без обращения к моделям.

**Экономия:** при 34 именах разница между «всё ежемесячно» и «по событию» —
десятки долларов в месяц и, что важнее, отсутствие потока отчётов, которые никто
не читает.

**Оценка:** польза высокая. Рекомендуется; это и есть заявленная цель проекта
(«выход в рабочий режим»).

## 7. Ценовые алерты без LLM

**Сейчас:** алерты не реализованы.

**Предложение:** сравнение цены с порогами лестницы — чистая арифметика над базой,
без единого обращения к модели. Стоимость нулевая, надёжность полная.

**Оценка:** очевидно. Реализовывать именно так.

---

## 8. Автономный агент: только заявка, без слияния и без доступа к боевой среде

**Сейчас:** агент открывает заявку, слияние делает человек, доступа к боевой среде нет.

**Предложение:** зафиксировать это как неизменяемое правило, а не как временную
осторожность. Плюс жёсткий потолок шагов и ограничение прав вместо инструкций
в тексте — вывод сделан из инцидента 05.08, когда текстовый запрет читать репозиторий
был проигнорирован, потому что не был подкреплён правами.

**Оценка:** обязательно.

## Чего в этом списке нет и почему

**Система проверок (490 тестов, 108 мутаций) не предлагается к сокращению**, хотя это
самый очевидный кандидат для внешнего критика.

Аргумент за сокращение: беспрецедентный объём для проекта одного человека; скорость
разработки страдает.

Аргумент против: каждая проверка заведена конкретным дефектом; за последнюю неделю
проверки поймали не менее четырёх ошибок, две из которых были денежными.

Контраргумент к аргументу против, который аудитору стоит проверить самостоятельно:
самый дорогой дефект скоринга (нулевой долг) **не был пойман ни одной из 490 проверок** —
его нашёл человек при чтении отчёта. Это ставит под вопрос не количество проверок,
а их распределение: они охраняют механику и почти не охраняют правдоподобие результата.

Это и есть вопрос, который архитектор системы не может решить о себе сам.
