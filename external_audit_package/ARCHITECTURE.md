## 3. Ключевые узлы и их роль

**Gather Data** — единственная точка обращения к EDGAR и рыночным источникам.
Публикует `_edgar` с CIK и названием эмитента.

**Verify FACT_PACK Entity** — гейт личности: сверяет CIK из эха модели с CIK из
первичных данных. Сравнение **числовое**, не строковое (SEC пишет `0001141391`,
модель — `1141391`). Несовпадение или отсутствие эха — жёсткий отказ до всякого
суждения. Заведён после случая, когда тикер `MA` был разрешён поисковым слоем как
штат Массачусетс, и это восемь дней не блокировало прогоны.

**Run Code** — вызов микросервиса; вся денежная арифметика здесь.

**Parse DI** — детерминированный пересчёт индекса расхождений из счётчиков арбитра.
Значение, написанное моделью, сохраняется канарейкой; при расхождении побеждает
вычисленное. Заведён после случая, когда модель написала итог 6.0 при сумме
слагаемых 3.0, и это заблокировало сделки.

**Assemble Report / Assemble Brief** — два ассемблера, машинный и человеческий.
Число ассемблеров пре-регистрировано и защищено пином: появление третьего краснит тест
и требует заново объявить список поверхностей публикации.

**Collect Usage** — учёт расходов и токенов по стадиям. Узлы без провайдера помечаются
`zero_by_construction`, отсутствующие на пути — `NOT_ON_PATH`.

## 4. Политики выполнения

| Свойство | Состояние |
|---|---|
| Повторы (retry) | заданы на HTTP-узлах качественного слоя (`retryOnFail`, `maxTries`) |
| Таймауты | на уровне узлов n8n; централизованной политики нет |
| Идемпотентность | **НЕ ОБЕСПЕЧЕНА.** Повторный запуск по тому же имени создаёт новый прогон и новый снимок |
| Кэширование | частичное, на уровне провайдеров; доля попаданий **не измеряется** |
| Сохранение состояния | снимки и учёт расходов в PostgreSQL; промежуточное состояние прогона не сохраняется |
| Восстановление после сбоя | **НЕ РЕАЛИЗОВАНО.** Прогон, упавший в середине, повторяется целиком |

## 5. Состояния отказа

| Состояние | Причина | Поведение |
|---|---|---|
| `RUNNER_ERROR` | нет цены, роста или множителя | расчёт не выполняется |
| `Category-F` | нет положительной прибыли и потока | уход на ветку Core-V |
| `FACTPACK_ENTITY_MISMATCH` | CIK эха не совпал | отказ до суждения |
| `FACTPACK_ENTITY_UNVERIFIED` | нет эха или нет CIK для сверки | отказ до суждения |
| `SOURCE_CALL_FAILED` | недоступен источник качественного слоя | тема помечена, прогон живёт |
| `MERGE_COLLISION` | один раздел пришёл из двух вызовов | явный отказ, не выбор победителя |
| `PARSER` | ответ модели не разобран | прогон уходит в доработку |
| `SINGLE_LEG_RUN` | построилась одна нога из двух | вердикт по единственной, объявляется |
| `CONTRACT_DEFECT_*` | отсутствует поле контракта | явный маркер, не тихий откат |

## 8. Почему бизнес-логика живёт в n8n, а не в Python-пакете

Историческая причина: проект начинался как последовательность вызовов в n8n, и логика
нарастала внутри узлов кода по мере усложнения. Осознанного решения «держать логику
в оркестраторе» не принималось — **RATIONALE_NOT_RECORDED**.

Наблюдаемые издержки:

- узлы кода хранятся строками внутри JSON; отдельные строки достигают 58 000 символов;
- правки узлов делаются вставкой в JSON и трижды ломались из-за экранирования;
- сравнение версий воркфлоу практически нечитаемо;
- проверки на узлы приходится писать через разбор JSON, а не как обычные тесты;
- чтение воркфлоу переполняет контекст участников — прямая причина нескольких
  вынужденных передач работы между чатами.

Предложение о выносе логики в Python-пакет — `SIMPLIFICATION_PROPOSAL.md` §1.
