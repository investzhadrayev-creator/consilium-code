# Диагностика: пустые ряды edgar_facts.py у GOOG (мультикласс) и NVO/DLO/SHOP/NBIS (иностранные эмитенты)

Карточка: issue #35 (диагностика, без правок кода). Родительская карточка: issue #34.

Все числа и факты ниже — прямой вывод SEC EDGAR `data.sec.gov` (submissions API, XBRL
companyfacts/companyconcept API, и разобранные R-файлы отчётов) и чтения
`CONSILIUM_REPO_v4_2_83/microservice/edgar_facts.py`, полученные в этой сессии через `curl` с
`User-Agent`. Ничего не взято из архива `Reports/histrun_2026-08-08/` и не додумано. Там, где
проверка не удалась, это указано явно.

| Тикер | CIK | Годовая форма (актуально) | Годовая форма на 2022-10-12 (as_of архива #34) | Таксономия XBRL |
|---|---|---|---|---|

Источники: `data.sec.gov/submissions/CIK{cik}.json` (счётчик форм по каждому имени) и

Важная деталь по SHOP, не фигурировавшая в формулировке карточки: Shopify не был "40-F всегда".
Хронология по `submissions`: `20-F` (2016-02-17, первый год после IPO) → `40-F` ежегодно

+ квартальные `10-Q`. То есть Shopify перестал быть iностранным частным эмитентом и стал
внутренним (domestic) подателем только с FY2024. На дату архива (as_of 2022-10-12) релевантна
форма **40-F** (FY2021, подана 2022-02-16) — не 10-K.

## 2. Гипотеза (а) — фильтр форм: ПОДТВЕРЖДЕНА

`microservice/edgar_facts.py` принимает факт только если `f.get("form","").startswith("10-K")` —
это условие встречается четыре раза (строки 279, 371, 550, 658 в `_annual_merged`,
`_detect_confirmed_splits`, и ещё в двух местах последовательно), плюс `_latest_instant` по
умолчанию берёт формы `("10-K", "10-Q")` (строка 583). Ни `20-F`, ни `40-F` нигде не входят ни в
один из этих списков.

Для SHOP/NVO/DLO/NBIS на as_of архива это отсекает **весь** ряд компании целиком, а не отдельные
поля — что и наблюдалось в #34 (`_missing` у всех финансовых полей). Причина буквальная: у этих
четырёх имён на релевантную дату **нет ни одного факта с формой, начинающейся на "10-K"** — есть
только `20-F` (NVO/DLO/NBIS) или `40-F` (SHOP). Гипотеза (а) полностью объясняет SHOP/NVO/DLO/NBIS.

Для GOOG гипотеза (а) **не применима**: GOOGL всегда подаёт обычный 10-K (подтверждено —
`10-K 2022-02-02`, `2023-02-03`, `2024-01-31`, `2025-02-05`, `2026-02-05`), фильтр по форме здесь
ничего не отсекает.

## 3. Гипотеза (б) — дименсиональность shares_diluted у GOOG: ПОДТВЕРЖДЕНА, механизм точнее гипотезы из #34

Проверено на реальном XBRL-инстансе 10-K за FY2021 (подан 2022-02-02, accession
`0001652044-22-000019`, релевантен as_of 2022-10-12) и 10-K за FY2024 (подан 2025-02-05, accession
`0001652044-25-000014`).

**Факт 1.** `data.sec.gov/api/xbrl/companyconcept/CIK0001652044/us-gaap/WeightedAverageNumberOfDilutedSharesOutstanding.json`
и аналогичный запрос для `WeightedAverageNumberOfSharesOutstandingBasic` возвращают значения
**только начиная с периода, оканчивающегося 2022-12-31**, и только из 10-K/10-Q, поданных
**2025-02-05 и позже**. Ни одной точки за FY2019–FY2021 нет вообще, хотя `EarningsPerShareDiluted`
(готовое значение EPS, не количество акций) присутствует непрерывно с 2013 года.

**Факт 2.** Разбор R-файла `R73.htm` (таблица "Net Income Per Share — Schedule of Earnings Per
Share") из 10-K за FY2021 показывает, что раскрытие числа акций для расчёта diluted EPS дано
**только в разбивке по классам** — Class A Common Stock / Class B Common Stock / Class C Capital
Stock — каждый со своей строкой `Number of shares used in per share computation`:

```
                                    FY2021    FY2020    FY2019   (тыс. акций)
Class A — used in diluted comp.    345,755   346,084   346,342
Class B — used in diluted comp.     45,430    46,182    46,527
Class C — used in diluted comp.    331,919   340,944   352,214
```

Ни агрегированной (недименсиональной) строки "diluted shares — компания в целом", ни за FY2021,
ни за FY2020/FY2019 в этой таблице нет. XBRL companyfacts/companyconcept API (на нём построен
`edgar_facts.py`) по конструкции отдаёт только недименсиональные ("default context") факты — факты
с осевым измерением (здесь — по классу акций) в него не попадают. Это подтверждено эмпирически
Фактом 1: агрегата за 2019–2021 просто нет ни в одном созвучном тег-запросе.

**Факт 3.** В 10-K за FY2024 (подан 2025-02-05) формат раскрытия ИЗМЕНИЛСЯ: перед разбивкой по
классам появился новый агрегированный блок с собственной недименсиональной строкой
`Number of shares used in per share computation`: **12,319 / 12,630 / 13,063** (basic,
FY2024/23/22) и **12,447 / 12,722 / 13,159** (diluted, FY2024/23/22, млн акций). Этот блок
ретроактивно переоформил и сравнительные FY2022–FY2023 — совпадает год-в-год с тем, что показал
Факт 1. Совпадение по времени с первым в истории Alphabet денежным дивидендом (`Allocation of
distributed earnings (cash dividends paid) $7,363` впервые появляется в этой же таблице за
FY2024) не проверено как причина документально (Alphabet не объясняет в самой таблице, почему
формат сменился) — это наблюдение, не подтверждённый факт.

**Вывод:** дименсиональность — не универсальное свойство GOOG, а свойство ПЕРИОДА. До 10-K,
поданного в феврале 2025 года, у Alphabet в XBRL нет недименсионального diluted-shares факта
вообще ни за один год; после — есть, и ретроактивно закрыт до FY2022. Для as_of 2022-10-12
(единственный доступный на тот момент отчёт — 10-K за FY2021) факта нет и не может быть в принципе
через companyfacts/companyconcept API, независимо от логики подбора общей даты в
`compute_eps_leg()` — что и заключила предыдущая сессия в #34.

## 4. Что пришлось бы менять в edgar_facts.py — по каждой подтверждённой причине, и чем это опасно

### 4.1 Причина (а) — форма 20-F/40-F не входит в фильтр

Минимальное изменение: добавить `"20-F"` и `"40-F"` в списки допустимых форм всюду, где сейчас
жёстко проверяется `startswith("10-K")` (4 места) и в `_latest_instant`'s дефолтный `forms`
tuple. Технически тривиально.

Риски:
- **`_detect_confirmed_splits`** (строка 371) построен на допущении "10-K, latest-filed wins,
  restatement-safe" — детектор подтверждённого сплита сравнивает повторные упоминания одной и той
  же даты конца периода в разных поданных 10-K. У 20-F/40-F эмитентов сравнительный период и
  частота переиздания (реструктуризация после AFS/IFRS-конвертации, например) могут не совпадать с
  этим допущением 1:1 — untested на реальных данных в рамках этой карточки (нужны отдельные пины
  на реальном повторном раскрытии, а не только на форме 10-K, как сейчас в `tests/fixtures/`).
- **`f.get("form") != "10-K"` для длительности >=300 дней** (строка 658, комментарий "annual
  duration facts only: 10-K, period >= 300 days") — расширение на 20-F/40-F меняет и это условие;
  20-F может нести полугодовые/промежуточные периоды (6-K заполняет кварталы, но сам 20-F тоже
  иногда несёт неполные периоды после смены отчётного года) — нужно валидировать длительность
  отдельно от формы, а не полагаться на "форма 10-K => обязательно годовой период".
- Это меняет поведение **для всех** тикеров, а не только для GOOG/SHOP/NVO/DLO/NBIS — любой
  ADR/иностранный эмитент в портфеле получит другую историю фактов. Карточка #35 требует не
  трогать код, но если такая правка будет предложена отдельной карточкой — она СТРУКТУРНО не
  ограничивается одним тикером и требует прогона по всему покрытию, а не только по 5 именам.

### 4.2 Причина (б) — дименсиональные факты у GOOG (только для периодов до FY2022)

Companyfacts/companyconcept SEC API **не отдаёт дименсиональные факты вообще** — обойти это можно
только (1) читать сырой XBRL-инстанс фильтров (`goog-20211231_htm.xml` и подобные) и вручную
суммировать по member'ам оси класса акций, либо (2) для is_annual-снапшотов старше FY2022 честно
возвращать null с именованным отказом "shares_diluted недоступен как агрегат в XBRL API для этого
периода" вместо текущего generic "no common FY end".

Риски варианта (1) — суммирование по классам:
- Числа по классам **не аддитивны напрямую** как "общее число акций компании". Метод two-class
  (per-class if-converted) в раскрытии Alphabet даёт для Class A denominator, УЖЕ включающий
  гипотетическую конвертацию Class B→A, и отдельно Class C denominator с другим набором
  допущений — сумма трёх строк "Number of shares used in per share computation" НЕ равна
  фактическому единому количеству акций компании (это видно из масштаба: Class A 345,755 тыс. +
  Class B 45,430 тыс. + Class C 331,919 тыс. = 723,104 тыс., тогда как реальное количество акций
  Alphabet на конец 2021 года — около 662–670 млн, то есть сумма классов systematически завышена
  за счёт двойного учёта конвертируемых Class B). Подстановка такой суммы вместо честного отказа
  была бы именно тем "изобретённым числом", что запрещено правилом CLAUDE.md "Honest failure beats
  an invented number".
- Чтение сырого XBRL-инстанса — это архитектурно другой источник (не JSON API SEC, а сам XML/iXBRL
  документ филинга), с другим форматом парсинга, другими сбоями (не по HTTP-статусу, а по XML-
  структуре), и без готовой кэш-инфраструктуры `_FACTS_CACHE`/`_CONCEPT_CACHE` — это не правка
  внутри существующей функции, а новый слой сбора данных.

### 4.3 Отдельно: IFRS-теги — DURATION_TAGS["net_income"] уже содержит "ProfitLoss", но это мёртвый код

`edgar_facts.py:64` уже перечисляет `"ProfitLoss"` как fallback-тег для `net_income` (видимо, в
расчёте на IFRS-эмитентов вроде NVO/DLO). Но каждый вызов `_annual_merged`/`_concept` использует
`taxonomy="us-gaap"` по умолчанию, и **ни один call site в файле не передаёт `taxonomy="ifrs-full"`**
(проверено `grep -n taxonomy= microservice/edgar_facts.py` — нет ни одного переопределения). Тег
`ProfitLoss` реально лежит у NVO/DLO в пространстве имён `ifrs-full`, а не `us-gaap`
(`facts["facts"]["ifrs-full"]["ProfitLoss"]`) — при текущем коде `_concept(facts, "us-gaap",
"ProfitLoss")` его никогда не найдёт, даже если форму 20-F добавить в фильтр. Это самостоятельный,
второй по счёту, пробел — независимый от фильтра форм.

## 5. Сопоставимость 20-F с 10-K: НЕТ единого ответа, нужен отдельный режим для IFRS-эмитентов

Проверка компанией по компании (`facts` → ключи таксономий в companyfacts JSON):

| Тикер | Таксономия | Что это значит |
|---|---|---|
| NBIS | **us-gaap** (520 тегов) | US GAAP, несмотря на форму 20-F — те же названия концептов, что и у 10-K-эмитентов (`Revenues` с FY2009 по FY2025, `NetIncomeLoss` с FY2009, `WeightedAverageNumberOfDilutedSharesOutstanding` с FY2009). Расширение фильтра форм (п. 4.1) для этого имени, вероятно, **достаточно само по себе** — тег-мэппинг менять не нужно. |
| SHOP | **us-gaap** (355 тегов) | US GAAP на всём протяжении истории, включая эру 40-F. НО конкретный тег для revenue отличается по эрам: `RevenueFromContractWithCustomerExcludingAssessedTax` встречается только у форм `40-F` (2017–2023), тег `Revenues` — только у форм `10-K`/`10-Q` (с 2022 по текущий, где 2022–2023 — сравнительные периоды в новых отчётах). Оба тега уже в fallback-списке `DURATION_TAGS["revenue"]`, так что при простом расширении формы это, вероятно, сработает — но не проверено на факте пересечения таксономии/формы построчно для каждого года, это гипотеза по структуре данных, не прогон через сам `edgar_facts.py` (карточка запрещает менять/гонять код). |
| NVO | **ifrs-full** (253 тега), 0 тегов `us-gaap` | Чистый IFRS. Ключевые концепты: `Revenue` (не `RevenueFromContractWithCustomerExcludingAssessedTax`), `ProfitLoss` (не `NetIncomeLoss`), `WeightedAverageShares`/`AdjustedWeightedAverageShares` (не `WeightedAverageNumberOfDilutedSharesOutstanding`), `DilutedEarningsLossPerShare`. Расширение фильтра форм НИЧЕГО не даёт без параллельной IFRS-таблицы тегов и без переключения `taxonomy=` на `ifrs-full` в вызовах. |
| DLO | **ifrs-full** (236 тегов), 0 тегов `us-gaap` | То же самое, что NVO: `Revenue`, `ProfitLoss`, `WeightedAverageShares`, `DilutedEarningsLossPerShare`. |

Ответ на прямой вопрос карточки: **добавление формы 20-F само по себе не делает NVO/DLO
сопоставимыми с 10-K-эмитентами** — это не вопрос формы, а полностью другая система тегов (IFRS
vs US GAAP), причём составы этих статей содержательно не идентичны построчно (IFRS не требует той
же детализации ASC 606 revenue disaggregation, иначе трактует аренду/обесценение/OCI и т.д. — сама
SEC не публикует таблицу переходников между ifrs-full и us-gaap, это была бы отдельная методическая
работа, не разбор одной карточки). Для NVO/DLO (и любых будущих чисто-IFRS имён) нужен отдельный
режим: своя таблица тегов, свой `taxonomy="ifrs-full"` путь вызова, и, вероятно, отдельная
пометка basis в выходных данных ("IFRS ProfitLoss ≠ US GAAP NetIncomeLoss по составу" — в духе
правила CLAUDE.md "the basis travels with the number, or the number is a lie").

Для NBIS и, вероятно, для SHOP (у обоих 20-F/40-F, но факты — в `us-gaap`) отдельный режим,
по всей видимости, не требуется — расширения списка допустимых форм может быть достаточно; но это
не подтверждено прогоном самого `edgar_facts.py` (запрещено объёмом этой карточки), только
структурой companyfacts JSON.

## 6. Что не проверено / ограничения этой диагностики

- Не проверено на живом прогоне `edgar_facts.py` — карточка требует только диагностику, код не
  менялся и не запускался с изменёнными данными.
- Гипотеза о причине смены формата раскрытия GOOG (первый дивиденд Alphabet в 2024) — это
  наблюдение по совпадению дат в двух R-файлах, не подтверждённое явным заявлением компании; в
  тексте раздела 3 помечено как непроверенное.
- Для SHOP не проверено год-в-год, что каждая из релевантных исторических as_of-дат (не только
  2022-10-12) действительно попадает в 40-F-эру, а не в переходный период 2024–2025 — проверена
  только сама архивная дата из #34.
- Полное построчное сопоставление IFRS-концептов NVO/DLO с US-GAAP эквивалентами (насколько
  идентичен состав `Revenue`/`ProfitLoss`) не выполнялось — это отдельная бухгалтерская экспертиза,
  не задача этой карточки; здесь зафиксирован только факт разных таксономий и разных имён тегов.
- Сетевой доступ к `data.sec.gov` в этой сессии был доступен через `curl` (в отличие от прошлой
  сессии в #34, где WebFetch к SEC был недоступен) — все цифры в этом документе получены оттуда
  напрямую в рамках текущей сессии, не из архива и не по памяти.
